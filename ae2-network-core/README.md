# AE2 network core: experimental subset

This is a standalone Rust experiment derived from Applied Energistics 2 commit `db17504a86128fdf3dae31f5fb7a112a646e0b93`, copyright AlgorithmX2 and AE2 contributors, under LGPL-3.0-or-later. See `LICENSE`. It is not a complete AE2 implementation, a Java compatibility layer, or an integrated game feature.

## Host contract

`Network` is serde-serializable, with `nodes: BTreeMap<Pos, Device>`. `Pos` uses block coordinates; use a separate `Network` per dimension. Each device occupies one block position in this initial model. Use `Device::new(kind)`, update nodes when blocks change, persist the network in the associated world, and call `validate` after loading. Validation rejects nonfinite, negative, or over-capacity energy; deserialization rejects duplicate positions. `insert_energy(pos, amount)` deposits AE into reachable finite buffers and returns the actual accepted amount; it never generates energy. Convert FE to AE and debit the real source in the host. `tick()` deducts one tick's idle usage from those buffers and returns current status. `analyze()` is a read-only status snapshot. Host must honor each `NodeStatus.online` before operating a device; the graph alone does not move items or perform crafting.

## Source basis and limits

- `me/pathfinding/ControllerValidator.java`: directly connected controllers, bounding box at most 7 blocks per axis, no crossings on two axes.
- `me/service/PathingService.java`: a controller-free network with more than eight channel-requiring nodes assigns no channels; per-channel-block power is 1/128 AE/t.
- `me/GridNode.java`: ordinary capacity 8, dense capacity 32, normal channel mode.
- `blockentity/networking/ControllerBlockEntity.java` and `core/definitions/AEBlocks.java`: controller buffer 8,000 AE, energy cell 200,000 AE, dense energy cell 1,600,000 AE. Energy acceptors and vibration chambers do not store energy; a host can call `insert_energy` at a vibration chamber to inject explicitly generated AE into connected buffers. Fuel consumption and exact generation rates are the host’s responsibility.
- `parts/networking/CablePart.java`, `parts/reporting/AbstractReportingPart.java`, `blockentity/networking/EnergyAcceptorBlockEntity.java`, `EnergyCellBlockEntity.java`: cable/cell/acceptor idle 0, terminal 0.5 AE/t, controller 3 AE/t. Other devices initially use the default 1 AE/t; real drives have dynamic per-cell consumption.

Controller networks use a deterministic controller-rooted tree with queues prioritizing dense cables, normal cables, then other nodes, and enforce each cable's capacity. This follows the broad source strategy but remains an approximation, especially in loops, P2P tunnels, dense-to-normal transitions, multiblocks and controller ports. Channel power counts each traversed node and connection. Controller-free accounting follows the source's node-count times assigned-channel count. Power on/off is approximated by whether buffered AE covers the next full idle tick; AE2's thresholds, grid internal energy buffer, extraction priorities, FE conversion and throughput limits are not implemented. Even a conflict can consume idle energy in this model.

A cable can hold up to six channel-requiring `AttachedPart` entries; the host provides a unique face and idle usage and checks `NodeStatus.parts[face].online`. The cable remains a routing node independently of its parts. Routing and channel power are approximations; general multipart geometry and connectivity, non-channel parts, chunk loading, grid splits/merges with energy redistribution, and arbitrary co-located devices are not modeled. Each device has color and six exposed-face bits; transparent connects to any color, otherwise colors must match. Adjacent exposed nodes connect when colors match, including ordinary machines; controller-connected channel routing allows ordinary non-controller nodes to carry channels, subject to their eight-channel capacity. Host-provided face masks must reflect actual machine orientation and formed state. Dense cables do not reproduce connection restrictions. CPU multiblock grouping, crafting, storage inventories, bus filtering/transfer, security, P2P, wireless, fluids, fuel inventory, exact vibration-chamber scheduling and true game UI remain host/integration work. Energy and channels here must never be presented as proof those behaviors work.

Tests: `cargo test --offline`.

`VibrationChamber` serializes fuel ticks and adaptive burn speed, with source-default settings and upgrade counts. `add_fuel` records fuel only after the host actually consumes an item; `advance` generates from elapsed game ticks and returns fuel spent, AE generated, and AE accepted. It reproduces the source ramp formula and overflow loss, while the host is responsible for machine wake/sleep scheduling and persistent fuel inventory. `P2pService` offers type- and frequency-filtered input/output lookup for one carrier grid; duplicate input frequencies are rejected and no transport or ME compressed-channel topology is implemented.

`PoweredMachine` models the zero-idle, non-channel main nodes in upstream `blockentity/misc/InscriberBlockEntity.java`, `ChargerBlockEntity.java` and `blockentity/crafting/MolecularAssemblerBlockEntity.java`. Attached reporting parts use 0.5 AE/t from `parts/reporting/AbstractReportingPart.java`; upgradeable bus parts require a channel (`parts/automation/UpgradeablePart.java`) and use the default 1 AE/t (`me/ManagedGridNode.java`). The host selects the appropriate values.

Upstream `InWorldGridNode.findInWorldConnections` connects mutually exposed adjacent nodes by compatible color; `GridNode.getMaxChannels` uses eight by default unless flags alter it. Drive front face is excluded by `DriveBlockEntity.getGridConnectableSides`; host must map orientation correctly. Unformed crafting units expose no sides, per `CraftingBlockEntity`. Crafting block node idle defaults to 1 AE/t in `ManagedGridNode`; no override is present in `CraftingBlockEntity` (cluster accounting is not fully modeled).
